## Findings

1. **Claude arms cannot edit files (blocker for meaningful Claude A/B).** The Claude adapter passes no permission mode, so headless `claude -p` blocks `Edit` and most `Bash`. The agent answered: "The permission system blocked the edit to index.js, so the TODO is still there." Both arms are no-ops, so the comparison and verdict are meaningless. Unit tests did not catch it (fake processes). Codex is fine because the adapter passes `-s workspace-write`. Fix proposed to the user: `--permission-mode acceptEdits` plus an allow-list of tools (edit/write/read tools and the detected project test command), not `bypassPermissions` (Lite has no filesystem isolation, canaries only detect).
2. **The Codex CLI writes to the real `~/.codex/config.toml`.** For every cwd it runs in (`a-0`, `b-0`, `base` of each run) it appends `[projects."<path>"] trust_level = "trusted"`, even with `--ignore-user-config`. somm does not write it. The entries accumulate (30 `[projects]` tables at check time, including leftovers from earlier smoke attempts) and point to deleted temp paths. Known class of limit (spec 5.2: CLIs write their own state to real config folders). Mitigation options: document it, or prune `somm-*` project entries after runs only with explicit user consent (somm must not rewrite `~/.codex` silently).
3. Isolation held in practice: Claude A/B inventories contained only built-in skills plus the probe; no user skills, plugins or MCP servers were loaded (`--setting-sources project,local --strict-mcp-config` works as in T1). Codex residue is listed and shown, as specified in spec 5.3.
4. Cheap models are fine for this smoke: the plumbing (detect, residue, arms, tests, canaries, verdict parsing, cleanup, save) worked with haiku and luna. Verdict wording quality was not evaluated.
